# 阈值工作点与不确定性（任务 F）

> 对应计划 `docs/OPTIMIZATION_PLAN.md` §5.1（按类工作点）、§5.2（bootstrap 区间）与 §9.3 任务 F。
> 数据源：`experiment_data/06_optimization/00_baseline/mvtec_seed_000/native/scores/*.json`（协议基线，`a38d1f7`，seed 0 / split_seed 42）。
> 产物：`experiment_data/06_optimization/06_threshold/bootstrap_seed_000/`（`config.json`、`metrics.json`、`per_class.csv`、`summary.csv`、`timing.json`、`run.log`）。
> 所有数字为 **development-only**：MVTec test 已被反复查看，本文不构成独立 holdout 结论。

## 1. 这份文档回答三个问题

1. 把目标误报率定在 0.5%，**实测落点**和区间是多少？
2. 按类选 FPR 是否比统一 FPR 更好？这个选择能否迁移到没参与选点的那一半？
3. 在预先声明的成本下，成本最优的工作点在哪，离 0.5% 有多远？

## 2. 协议

| 项目 | 取值 |
|---|---|
| 阈值来源 | 每类 `calib`（留出良品）经验分位：`thr = P100(1-fpr)` |
| 灰区 | `thr_ng = 1.2 × thr_ok`，`[thr_ok, thr_ng)` 判复核 |
| 划分 | test 按路径排序后隔一取半：前半 validation（选点用），后半 test（只评估一次） |
| 成本 | 漏检 100、过杀 10、复核 1；先验不良率 1% |
| bootstrap | 1000 次，同时重采样 calib（重建阈值）与评估半集（重建各率）；按类模式还会重采样 validation 并**重新选点** |
| 区间 | P2.5–P97.5（不是置信保证），同时给 P50 |

两点必须写清：

- **这不是 conformal 保证**。`docs/conformal-thresholds.md` 已证明：`k = ceil((n+1)(1-α))`，0.5% 需要至少 199 张标定良品；本基线每类只有 18–117 张，**15 类全部不可达**（α_min 0.85%–5.26%）。
- **这不是独立 validation**。原始 test 已参与多轮开发，这里的两半都只能算 development；「按 validation 选点、test 只报一次」在本机只能做到流程隔离，做不到数据独立。

## 3. 结果一：0.5% 的实测落点

统一目标 `fpr=0.005`，在评估半集上的实现值：

| 模式 | macro FPR | macro 漏检 | macro 复核 | macro 成本/件 |
|---|---|---|---|---|
| 统一 FPR | 3.31% | 43.81% | 21.79% | 0.8011 |
| 按类 FPR | 5.35% | 36.88% | 22.55% | 0.9507 |

区间（1000 次 bootstrap，macro 的 P2.5 / P50 / P97.5）：

| 量 | 统一 FPR | 按类 FPR |
|---|---|---|
| FPR | 0.0% / 3.98% / 22.2% | 0.0% / 7.28% / 30.2% |
| 漏检 | 25.4% / 42.1% / 57.7% | 19.4% / 35.6% / 52.0% |
| 成本/件 | 0.293 / 0.875 / 2.861 | 0.253 / 1.141 / 3.586 |

**读法**：目标 0.5%，实测 3.31%，区间 0%–22%。原因不在算法，而在样本量——评估半集的良品只有 **6–30 张**（最少的 toothbrush 6 张、bottle/wood 各 10 张），一张良品被判过杀就是 3–17 个百分点的 FPR。**在本机，「0.5% 过杀」只能作为业务档位标签，不能作为已测得的属性对外报。**

## 5. 结果二：按类 FPR 选点不能迁移

- 选点结果分散：`0.002 ×4、0.005 ×3、0.02 ×3、0.05 ×4、0.1 ×1`，**8/15 类选了比 0.5% 更宽的目标**。
- 选点不稳：对同一类重采样 validation 后，被选中的 FPR 档位平均只有 **53%** 的复现率（最低 24%）——一半以上的 bootstrap 会换一个档位。
- 迁移失败：在未参与选点的 test 半集上，按类模式成本 **0.9507 > 0.8011**（统一模式），且成本区间更宽（2.57 vs 3.33 /件）。

结论：**在这批样本上，按类 FPR 调优是噪声放大，不构成改进**。计划 §5.1 的「按类工作点」在本机无法验证成立，只能作为「需要更多 validation 数据」的待办。

## 6. 结果三：成本-精度前沿（统一 FPR，点估计）

| 目标 FPR | 实测 macro FPR | macro 漏检 | macro 复核 | macro 成本/件 |
|---|---|---|---|---|
| 0.2% | 3.31% | 46.28% | 22.3% | 0.826 |
| 0.5% | 3.31% | 43.81% | 21.8% | 0.801 |
| 1% | 3.97% | 41.59% | 22.5% | 0.852 |
| 2% | 5.89% | 38.07% | 22.8% | 1.021 |
| 5% | 17.66% | 33.13% | 24.4% | 2.253 |
| 10% | 23.88% | 27.01% | 23.8% | 2.869 |

成本在 **0.2%–1%** 区间几乎持平（0.80–0.85），说明在这个成本结构（漏检:过杀 = 100:10、先验 1%）下，0.5% 与 1% 的差别小于测量噪声；再往上放宽，过杀成本开始主导。

## 7. 结论与建议

1. **保留统一 FPR 作为档位，不要按类调**；把「0.5%」标成业务目标而非实测属性。
2. **任何「0.5% 保证」的话术都不能用**：conformal 需要 ≥199 张标定良品，本机 15 类全部不可达（最接近的 hazelnut 需 117 张才到 0.85%）。
3. 若面试被问「阈值怎么定」：现在的答案是「经验分位 + 成本表 + bootstrap 区间，0.5% 是目标不是保证；改判定成本会让最优点在 0.5%–20% 之间移动」（见 `docs/cost-model.md`）。
4. 想真正验证按类工作点，需要每类 ≥200 张独立良品与 ≥100 张独立缺陷，本机数据不够——这是数据问题，不是调参问题。

## 8. 局限

- 评估半集良品仅 6–30 张，FPR 的分辨率是 3–17 个百分点；任何小数位差异都不该被解读。
- 两半都来自已参与开发的 test 集，只能称 development 流程隔离。
- 成本参数（100/10/1、先验 1%）是预声明假设，换一组权重最优点会移动，`docs/cost-model.md` 有敏感度表。
- bootstrap 只量化抽样噪声，不含模型换 seed 的方差（后者见 `docs/coreset-budget.md`、`docs/features-ablation.md`）。
- 增强样本未纳入（计划要求另存为敏感性实验），因此本文的 calib 计数就是原始留出良品数。

## 9. 复现

```powershell
cd E:\面试项目文件夹\patchcore-mvtec
.venv\Scripts\python.exe tools/threshold_ci.py `
  --scores experiment_data/06_optimization/00_baseline/mvtec_seed_000/native/scores `
  --out experiment_data/06_optimization/06_threshold/bootstrap_seed_000 `
  --fpr 0.005 --repeats 1000 --seed 2026
```

单次运行约 14 秒（纯 numpy，无 GPU）。改变成本/先验/grid 时，`config.json` 会记录命令，结果目录需要换新的 `seed_NNN`。
